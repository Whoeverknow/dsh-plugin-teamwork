# 多 Agent × Teamwork：四线研讨

> 素材来源：Google Antigravity 官方博客《Teamwork: When AI Becomes a Research Partner》(2026-08-27) 及 `/docs/teamwork` 文档（均为厂商发布材料，未经独立验证）；DSH 运行时实测的 `agentTeams`/`workflowEngine`/`subagents`/`goals` 等服务契约。
> 本文是「理论 → 验证 → 落地 → 实例」的完整论证链。

## 线一 · 理论谱系对照：哪些是真新，哪些是旧酒

把 Teamwork 的每个机制逐一对表：

| Teamwork 机制 | 旧根 | 新毛 | 判词 |
|---|---|---|---|
| GAS 循环（生成-对抗-合成） | 进化计算（变异-选择-重组，60 年） | 把循环规格化成可配置 pattern | 旧酒新瓶，瓶口设计确实好 |
| 锦标赛网络 | 遗传锦标赛选择 + AlphaGo self-play 改进 | 采样式读取候选+批判控制上下文；失败带异议重跑 | 有真实工程增量 |
| Falsifier 与候选配对 | 红队/对抗样本（安全领域） | 证伪前置到策略层且与候选 1:1 并行 | 前置化是结构创新 |
| Critic/Challenger/Auditor/Success Auditor 四层 | 软件工程 design review→code review→CI→release | 审计层专门核查"测试真的跑了而不是被 mock"（元验证） | 元验证是真新 |
| pattern=声明式规范 | 工作流 DSL | 编排与 agent 描述解耦、运行时自适应、机制跨域移植 | 把 DSL 从建模工具升级为可移植机制载体 |
| Pitfall Registry（answer-agnostic） | 经验回放 / 记忆增强 | 强制"与答案解耦"的负知识蒸馏 | 反过拟合训练，最认可的单点 |
| 完整性模式 | RLHF 安全护栏 | 把"禁止哪些捷径"（抄开源/外包/读测试源码）变成显式契约 | 治理规格化创新 |
| 人类定目标与最终验收 | 经典 HITL | 明确画成两个控制点 | 无新意但执行干净 |

**三个被包装成创新、其实是伪边界的点：**

1. **"编排解耦"≠"无需编排经验"**——pattern 可移植，但写 pattern 的人必须懂编排。解耦只把知识从"运行时模型"转移到"构建时系统"；代价是灵活性（图灵完备脚本能表达任意策略，pattern 只能表达已枚举的）。
2. **"自适应团队规模"≠"智能涌现"**——运行时加 agent 只是在调并行度参数；真正的自适应发生在分解（依赖图）上，不在 spawn 数量上。
3. **"验证分层"≠"验证增强"**——四层塔每层仍是同一验收标准，分层只改变失败在哪层被发现，不改变验证器本身的可靠度。

**DSH 在谱系中的坐标**：`subagent`=一次性委派、`workflow`=脚本编排、`ralph`=串行采样、`goals`=跨轮驱动、`agentTeams`=社会团队。缺的是"机制可移植层"——这正是插件的谱系学位置。

## 线二 · 验证与信任：多 Agent 的天花板定理

### 验证器硬度谱系

```
形式化工具 (Lean/SMT)  >  外部硬件 oracle (BOOM/Spike)  >  确定性脚本 (测试/基准)
  >  统计/采样评审 (多数投票)  >  同源 LLM 批判 (Falsifier/Critic)
```

### 天花板定理

> **团队智能的上限 = 验证器的可靠度，而不是成员的聪明度。**

任一改进闭环都是"生成 → 验证 → 基于验证改进"；验证不可靠则改进是噪声驱动，N 个 agent 只是把噪声分摊到 N 条路径上。best-of-N 的收益上限由验证器真阳性率决定，不由 N 决定。佐证：博客七个数学成果里唯一机器验证的（Knuth，Lean）最硬；其余六个靠人工专家——验证器换成人，规模收益立刻受限于人的吞吐。

### 验证器完整性四层面（Teamwork 做了三层，第四层被冷落）

| 层面 | 含义 | Teamwork | DSH 落点 |
|---|---|---|---|
| 信息隔离 | 被测方看不到验证器内部 | ✅ 沙箱 Spike、禁读测试源码 | `fs-sandbox` + 权限预设 + `writeScopes` |
| 参考隔离 | 验证数据与运行环境气隙 | ✅ air-gapped BOOM/Spike | 固定基准 fixture + hash 锁定 |
| 元验证 | 核查"验证真的执行了" | ✅ Auditor 查真实命令输出 | `tool-jobs` 输出审计 |
| 来源证据（provenance） | 每个结论可追溯"谁生成、谁验证、谁签字" | ❌ 未显式设计 | `agentTeams.updateTask` 的 revision CAS + ownerName 天然是审计链 |

→ 插件应把 provenance 做进默认：每个 "Accepted" 状态携带 `(candidateId, verifierId, evidenceRef, signature)`。

### 同源偏差的诚实处理

同族模型的"对抗"实际收益排序：**重新采样（真）> 链长（真）> 博弈（伪）**。工程结论：别把对抗当博弈，把它当"便宜的多样化重试 + 更长的验证链"；真正的异质验证器（确定性脚本、外部 oracle、形式化工具）永远优先。

### 静默失败间隙 → 连续验证（DSH 版本）

"silent execution gap"（数百周期静默分歧才暴露失败）推广为：**失败潜伏期越长，验证越必须连续**。DSH 等价机制：`goals`+`goal-round-driver`（周期性检查点）、`schedule`（定时回归）、`invariants`（持续断言，违反即停）、`tool-jobs`（增量输出）。插件组合成"连续验证心跳"：每个子任务完成即触发不变式+抽样回归，而非攒到最终 Global Verification。

## 线三 · 落地决策：边界、矩阵、骨架（摘要，详见 COMPARISON.md 与 DESIGN.md）

五条边界决策：① 不做角色底座只做 pattern 引擎；② 契约冻结前只做 thin 层；③ 验证主力=确定性验证器，LLM 批判=启发式；④ 预算进 Config 默认值且不可被模型覆盖；⑤ provenance 进默认。

## 线四 · 实例复盘

- **案例 A（该用）**：TS SDK 异步化重构 → distributed_coding：可分解✅、可验证✅（测试+基准=确定性 oracle）、错误代价中高、可归类✅。
- **案例 B（该用且验证器是瓶颈）**：开放数学猜想 → long_proof：验收门只信形式化工具/反例搜索，预算与并行度显式挂钩。
- **案例 C（不该用）**：单 bug 修复 → 单 Agent + 测试。插件全部开销换不来任何收益——判定矩阵第一章就是用来拦下它的。

## 收束

> **多 Agent 的正确性问题只有一个——你是谁在验证，以及验证有多硬。** 谱系决定组织方式，验证决定收益上限，上限再决定边界与预算。规模不决定上限，验证密度与信息效率决定上限。
